## Summary
Implements spec 0006: Masaniello profit target ($/%), live answer line, derived progress (history read + today's live sessions), Dashboard "Session x/y" counter, auto copy balance, three per mode alerts, `MS_STOP_LOSS` end reason behind a toggle, and removal of the Masaniello daily lock. The pure engine (`msSessionsToTarget`, `msTargetProgress`, `msCounterLabel`, `msTargetAnswer`) is clean, matches the spec math, and is well tested; all 37 tests in `src/Masaniello.test.js` pass. The headline gaps are the alert effect (the most stateful new code) having no test at all, and a midnight rollover hole in the derived progress that the spec claimed could not happen.

## Major
### 🟠 Alert effect rewrite is untested, `src/App.js:9187`
**Problem**: The session ended effect was reworked substantially: first load seeding (`prevSessionsForAlertRef` now starts `null`), the Masaniello branch, target reached flip seeding after history resolves (AC-15), the "one chime when end and target coincide" rule, the silent path when the cycle end toggle is off, and the Stop Loss once per cycle guard. None of it has a test. The panel tests only check that the toggles render with the right defaults.
**Why it matters**: This is branching, stateful logic with several "fire exactly once / never on load" invariants (AC-13 to AC-15). Regressions here mean repeated chimes on reload or missed alerts, which is exactly the bug the spec set out to fix. Spec "Critical test scenarios" lists the alert scenarios explicitly.
**Suggested fix**: Extract the decision part (given prev sessions, current sessions, prev reached map, settings, history -> list of {chime, notification} events) into a pure function and unit test it: no alerts on first run, cycle end toggle off is silent, coinciding end + target gives one chime with "Profit target reached", target flip not fired before history resolves, Stop Loss fires once.

### 🟠 Progress loses sessions across midnight, `src/App.js:9006`
**Problem**: History is read once per `${mode}:${setAt}` key (`msHistRequested` never re-requests) and holds only sessions ended before that read. Sessions that end later live only in `todaySS.sessions`. `getToday` (App.js:1051) returns an empty session list once the date changes, so for a tab left open past midnight every session ended since load drops out of `msMergeSessions`. The spec's "merged with live todaySS by session id, live wins, so a midnight rollover loses nothing" does not hold.
**Why it matters**: The Dashboard counter and the panel answer line show a lower count and profit (wrong number, against AC-6/AC-9) until reload. Worse, if the target was reached, `prevReachedRef` flips true -> false, and the next ended session flips it back, firing the "Profit target reached" alert a second time.
**Suggested fix**: Key the cache on the date too (e.g. `${mode}:${setAt}:${todaySS.date}`) so a new day triggers a fresh read, or append each just-ended Masaniello session into the `msHist` entry when it ends.

## Minor
### 🟡 Panel answer line ignores history status, `src/App.js:7626`
**Problem**: `MasanielloSettings` uses `msModeProgress(...)` regardless of `status`. While history is loading or after a failed read, profit so far counts only today's sessions, so the line shows a confident "About S sessions" with S too high. The Dashboard handles this (falls back to "Session x"), the panel does not.
**Why it matters**: AC-6 says the answer line never shows a wrong number.
**Suggested fix**: When the saved progress status is not `ok`, show a short loading/failed message or omit the session count.

### 🟡 Unit switch on an empty target dirties the draft, `src/App.js:7656`
**Problem**: Clicking `%` with an empty field writes `msTargetUnit` into the draft, making the Save bar dirty and persisting the unit with no value. AC-1 says "switching the unit on an empty field changes nothing".
**Suggested fix**: Either keep the unit as local UI state until a value exists, or accept it and adjust the spec wording.

### 🟡 Saved % target turns into an error when balance drops, `src/App.js:7575`
**Problem**: `msFieldErrors` validates a `%` target against the current balance even when the value is unchanged and dollars are already stored. If the balance later goes to 0 (or the percent now rounds under $0.01), the panel shows an error, hides the answer line, and the Save bar counts a skipped field on every save, although the stored dollar goal is valid and fixed (AC-2).
**Suggested fix**: Skip the balance based checks when value and unit equal the saved ones and `msTargetDollars` is set.

### 🟡 Stop loss alert ignores "Stop Loss ends cycle", `src/App.js:9230`
**Problem**: AC-13 says the Stop loss alert only matters while "Stop Loss ends cycle" is off. The alert path does not check `getMsStopLossEndsForMode`. Normally harmless (the crossing trade ends the session in the same snapshot), but the effect now also runs on `settings` changes, so lowering Stop Loss % mid cycle with the toggle on fires the stop loss alert while the cycle stays active until the next trade.
**Suggested fix**: Return early when `getMsStopLossEndsForMode(settings, s.accountMode)` is true.

### 🟡 Conditional assertion can pass vacuously, `src/Masaniello.test.js:307`
**Problem**: "an invalid target keeps the last saved target and start time" wraps its only `expect` in `if (saveSettings.mock.calls.length)`. If Save is not called, the test asserts nothing.
**Suggested fix**: Assert that save is (or is not) called, then assert the payload unconditionally.

### 🟡 History read and cache never reset on user change, `src/App.js:9006`
**Problem**: `msHist`, `msHistRequested`, `prevReachedRef`, `prevSessionsForAlertRef` survive a sign out / sign in in the same tab. A second user would skip seeding (alerts for their already ended sessions on load) and could, in theory, reuse a cache key.
**Suggested fix**: Reset these when `authUser?.id` changes.

### 🟡 `loadMsTargetHistory` and the history effect have no test, `src/App.js:1752`
**Problem**: The query shape (filters, ISO conversion, `msN` filter) and the loading/error status transitions are untested; only the merge and progress helpers are.
**Suggested fix**: One test with a mocked supabase client covering ok and error status.
