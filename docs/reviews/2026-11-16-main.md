## Summary
Adds a `Profile` page (account details, display name, change password, sign out, Settings link) backed purely by the Supabase auth user, a `Profile` nav item before Settings, and a one-rule change in the `App` auth listener so `USER_UPDATED` replaces the user object. No correctness or security bugs found; remaining gaps are untested spec scenarios (dirty-Settings leave guard, phone width) and a mixed-identity labelling edge case. `src/Profile.test.js` (14 tests) and the full suite (212 tests, 9 suites) pass.

## Minor
### 🟡 Sign in method label wrong for mixed identities, `src/App.js:9171`
**Problem**: `prov=providers[0]`. A user with identities `[google, email]` shows "Google" as the sign in method while the password form also shows (because `hasPw` is true).
**Why it matters**: Only email auth exists today, so low impact, but the row is described as a guard for exactly this future case and would be misleading.
**Suggested fix**: Prefer "Email and password" when `hasPw`, or list all providers joined.

### 🟡 Leave guard path from dirty Settings untested, `src/Profile.test.js:188`
**Problem**: Spec AC-1 and the "Navigation" critical scenario require that opening Profile (or Go to Settings) with a dirty Settings draft goes through the leave dialog. AC-11 test only covers the clean path.
**Why it matters**: The guard is shared branching logic; a regression there would drop unsaved settings silently.
**Suggested fix**: Add a test: dirty a Settings field, click the Profile nav item, assert the leave dialog appears.

### 🟡 AC-12 phone width not covered, `src/App.js:9212`
**Problem**: No test or recorded verification for the phone width criterion (single column, no sideways scroll, 40px targets). Scope also marks this step unchecked.
**Why it matters**: Spec acceptance criterion; jsdom cannot prove layout, so it needs `/check verify` in a real browser.
**Suggested fix**: Cover in `/check verify` at phone width before marking the feature done.
